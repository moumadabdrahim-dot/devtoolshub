Why Format SQL Queries?

SQL queries are often written as long, single-line strings — especially when generated by ORMs, copied from logs, or quickly typed in a console. While the database engine doesn't care about whitespace, humans do. Properly formatted SQL offers significant advantages:

  • Readability — Each clause on its own line makes the query's logic immediately clear.
  • Debugging — It's far easier to spot missing JOIN conditions, wrong WHERE clauses, or typos when the query is well-structured.
  • Code reviews — Reviewers can quickly scan formatted SQL and understand the intent without mentally parsing a wall of text.
  • Team consistency — A shared formatting standard eliminates style debates and makes diffs cleaner.
  • Documentation — Formatted queries serve as self-documenting code when included in wikis, READMEs, or runbooks.

SQL Formatting Best Practices

  1. One clause per line — Put SELECT, FROM, WHERE, JOIN, ORDER BY, etc. on separate lines.
  2. Indent sub-items — Column lists, conditions, and subquery bodies should be indented one level deeper than their parent clause.
  3. Uppercase keywords — Using SELECT instead of select visually distinguishes SQL keywords from table/column names.
  4. Align related items — Vertically aligning AND/OR conditions aids scanning.
  5. Break up long IN lists — Put each value on its own line or group them logically.
  6. Use aliases consistently — Alias tables with meaningful short names (u for users, o for orders) and always qualify column references.
  7. Comment complex logic — Add -- inline comments to explain non-obvious conditions or business rules.
-- Well-formatted example
SELECT
    u.id,
    u.name,
    COUNT(o.id) AS order_count
FROM
    users u
    INNER JOIN orders o ON o.user_id = u.id
WHERE
    u.active = 1
    AND o.created_at >= '2025-01-01'
GROUP BY
    u.id,
    u.name
ORDER BY
    order_count DESC
LIMIT
    10;

Frequently Asked Questions

Does this tool send my SQL to a server?

No. All formatting happens entirely in your browser using JavaScript. No data is uploaded, stored, or transmitted to any server. Your queries remain completely private.

Which SQL dialects does this formatter support?

The formatter handles standard ANSI SQL keywords and syntax. The dialect selector (MySQL, PostgreSQL) is provided for future dialect-specific formatting rules. Currently, all dialects share the same core formatting engine, which correctly handles all common SQL clauses, JOINs, subqueries, CTEs, comments, and string literals.

Does formatting change the meaning of my SQL?

No. The formatter only adds or removes whitespace and line breaks. It never modifies keywords, table names, column names, operators, values, or the logical structure of your query. The formatted output is semantically identical to the input.

Can I format stored procedures and DDL statements?

Yes. The formatter recognizes DDL keywords like CREATE TABLE, ALTER TABLE, CREATE INDEX, and DROP TABLE. It also handles INSERT INTO ... VALUES, UPDATE ... SET, and DELETE FROM. Complex procedural blocks (PL/pgSQL, T-SQL) may have limited support, but the core statement formatting works reliably.
